    2. Five different things: keep them apart

    ConceptWhat it doesIn the pipelineReversible?Involves a secret?
    Key generation Creates a new secret from true randomness (a CSPRNG). This is the only step that adds entropy. 128–256 random bits → BIP-39 entropy—Creates it
    Key derivation Computes further secrets deterministically from an existing secret. Same input, same keys, so one backup restores everything. PBKDF2 (mnemonic → seed), HMAC-SHA512 (seed → master key → child keys)No (one-way)Yes
    Public-key cryptography A key pair with a one-way link: the public key can be shared, the private key signs. Security rests on the ECDLP. secp256k1: private key k → public key K = k·G; ECDSA signs transactionsNo (ECDLP)The private key
    Hashing Maps any input to a fixed-size fingerprint. One-way, collision-resistant, avalanche effect. No key. Keccak-256 (address, EIP-55), SHA-256 (BIP-39 checksum), SHA-512 (inside HMAC/PBKDF2)NoNo
    Checksum A few redundant bits that detect accidental errors (typos). Not protection against attackers. BIP-39 last 4–8 bits; EIP-55 upper/lower case—No
    Encoding Changes only the representation of the same data. No security at all. bits → words, bytes → hex, 0x prefix, mixed caseYes, fullyNo

    Several steps combine two roles: a BIP-39 mnemonic is an encoding of the entropy plus a checksum, and EIP-55 is a checksum carried by an encoding (letter case).

    3. Role and purpose of each standard

    BIP-39 2013

    entropy ↔ mnemonic → seed

    Turns 128–256 random bits into 12–24 words from a 2048-word list (11 bits per word, plus a SHA-256 checksum). The words are stretched into a 512-bit seed with PBKDF2-HMAC-SHA512 (2048 rounds, salt "mnemonic" + optional passphrase).

    Purpose: a backup that humans can write down and type back without errors.

    BIP-32 2012

    seed → tree of keys

    Hierarchical deterministic (HD) wallets: HMAC-SHA512 turns the seed into a master key and a chain code, and then into an unlimited tree of child keys. Hardened children use the parent private key, normal children can also be derived from the parent public key (watch-only wallets).

    Purpose: one seed backs up a whole tree of keys, so there's no need to back up each key.

    BIP-44 2014

    which branch of the tree?

    Fixes the meaning of the path levels: m / purpose' / coin_type' / account' / change / address_index. Ethereum is coin type 60 (SLIP-44), so the first account is m/44'/60'/0'/0/0.

    Purpose: interoperability, so different wallets find the same addresses from the same phrase.

    secp256k1 SEC 2, 2000

    private key → public key

    The elliptic curve y² = x³ + 7 over a 256-bit prime field (the same curve as in HMWK 1, at full size). K = k·G is easy to compute and infeasible to invert, and ECDSA on this curve signs every Ethereum transaction.

    Purpose: prove ownership (signatures) without revealing the private key.

    Keccak-256 2012 / Ethereum 2015

    public key → address

    The sponge hash that won the SHA-3 competition, used in Ethereum with its original padding. The address is the last 20 bytes of Keccak-256(x ‖ y) of the 64-byte public key.

    Purpose: a short, fixed-size identifier that does not reveal the public key until the first signature.

    EIP-55 2016

    address → checksummed address

    Hashes the lowercase hex address with Keccak-256 and writes letter i in upper case when hash nibble i is ≥ 8. The address stays valid hex and backwards compatible.

    Purpose: catch typos before sending funds to a wrong address.

    4. Why several techniques instead of one algorithm?

    Each step solves a different problem, and the requirements conflict, so no single primitive can do all of them:

    • BIP-39 / BIP-32 / BIP-44 → key management and derivation. Humans need a short, robust backup (words + checksum), the wallet needs many keys from it (deterministic tree), and wallets need to agree where to look (standard paths). PBKDF2 is deliberately slow to make passphrase guessing harder, which would be a disaster for a hash used everywhere.
    • secp256k1 → public/private key relationship and signatures. It needs algebraic structure (k·G, (a + b)·G = a·G + b·G) so that signatures can be verified with the public key alone. A hash function has no such structure on purpose.
    • Keccak-256 → hashing. It needs no structure: a fast, keyless, one-way, collision-resistant fingerprint that compresses 64 bytes into 20 and looks random.
    • EIP-55 → checksum / error detection. It protects against human mistakes, not attackers, and must not change the address itself. Changing only the letter case gives about 15 check bits for free.

    The design separates concerns: randomness only at the start, secrecy only up to the private key, and public, keyless steps afterwards. Each primitive can be analysed (or replaced) on its own.

    5. SHA-2 / SHA-512 vs Keccak / SHA-3

    SHA-2 (SHA-256, SHA-512)Keccak / SHA-3
    Designers, yearNSA; NIST standard 2001Bertoni, Daemen, Peeters, Van Assche; won the NIST competition 2012, FIPS 202 in 2015
    ConstructionMerkle–Damgård: a compression function applied block by blockSponge: absorb input into a 1600-bit state, permute (Keccak-f), squeeze output
    Length extensionVulnerable (that is one reason HMAC exists)Not vulnerable
    In the wallet pipelineSHA-256: BIP-39 checksum. SHA-512: PBKDF2 (seed) and HMAC (BIP-32)Keccak-256: address and EIP-55 checksum

    Keccak-256 ≠ SHA3-256. NIST standardized Keccak as SHA-3 but added domain-separation bits to the padding: the byte appended to the message is 0x06 in SHA3-256 and 0x01 in the original Keccak. Ethereum adopted Keccak before FIPS 202 was final and kept the original padding. Same permutation, same rate, different output (older Solidity even called it sha3).

    6. Temporal and historical context

    1. 1976 Diffie–Hellman: the idea of public-key cryptography. context
    2. 1977 RSA: the first practical public-key cryptosystem (factoring).
    3. 1985 Koblitz and Miller propose elliptic-curve cryptography. context
    4. 2000 SEC 2 defines secp256k1; PBKDF2 published in RFC 2898. context
    5. 2001 SHA-2 (SHA-256, SHA-512) standardized by NIST.
    6. 2009 Bitcoin uses secp256k1 and SHA-256. context
    7. 2012 BIP-32: hierarchical deterministic wallets. Keccak wins the SHA-3 competition.
    8. 2013 BIP-39: mnemonic code for generating deterministic keys.
    9. 2014 BIP-44: multi-account HD wallets.
    10. 2015 SHA-3 standardized by NIST (FIPS 202). Ethereum launches with the original Keccak-256.
    11. 2016 EIP-55: mixed-case checksum addresses for Ethereum.

    The order shows how the pipeline grew: the primitives (public-key cryptography, SHA-2, elliptic curves) came from academic and government cryptography, while the wallet layers (BIP-32/39/44) were added by the Bitcoin community to solve key management. Ethereum then reused those wallet standards (coin type 60), chose Keccak for hashing, and added EIP-55 to fix the missing checksum in its addresses.

    TestMeasuredTheory

    What the statistics mean

    • Only the entropy is random. All later values are deterministic functions of the 128 random bits (plus the passphrase). They look uniform and pass the tests above, but they contain no extra randomness.
    • Hashing and key derivation spread every change. Seed, keys, hash and address change about 50% of their bits when one entropy bit flips (avalanche). Encoding steps do not: the mnemonic changes only in the flipped bit and a few checksum bits.
    • Uniform hex digits in the address are a property of Keccak-256 output. The public key's x coordinate is also close to uniform; its prefix byte (04) is fixed, so the raw encoding is not.
    • Checksums are about probability, not secrecy: 4 BIP-39 bits catch 15 of 16 wrong words; EIP-55 has about 15 case bits per address, so a random typo slips through with probability about 2⁻¹⁵. An all-lowercase address carries no checksum at all.
    • Expect some false alarms. At the 5% level, about 1 test in 20 "rejects" even for perfect random data. Run the experiment again and the rejection moves elsewhere. A real defect would reject consistently, and more strongly as the sample grows.
    • Tick "weak random generator" and run again: every statistic still looks perfect, yet there are only 65 536 possible wallets and an attacker can try them all in seconds. Statistical tests on the outputs cannot detect bad input randomness, because the hash functions hide it. Security comes from the unpredictability of the entropy, which is why wallets must use a cryptographic RNG.
